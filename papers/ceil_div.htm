Integer ceil division

An integer ceil division corresponds to (int) ceil((double) a / (double) b). This converts the values to double, divides them, and rounds the quotient up to the nearest integer. If you have a block size of 512 and want to calculate the number of blocks needed to store n bytes, then n ceilDiv 512 provides the answer.

Since floating-point operations are costly, the alternative for computing an integer ceil division is (a + b - 1) / b, which just uses integer computations. Another method is (a - 1) / b + 1. Both formulas assume that a and b are positive integers. For negative numbers, the computation becomes more sophisticated.

How often are integer ceil divisions used?

I searched my source code and found integer ceil divisions in 14 different libraries. In total, 45 integer ceil divisions were found. I did not expect to find so many. In all of these cases, one of the integer formulas mentioned above was used. While the code was correct and readable, a closer look was required to realize that an integer ceil division was actually being performed.

The libraries utilizing ceil division fell into three categories:

  • Libraries supporting graphics formats: JPEG, BMP, TIFF, ICO, TGA, and PBM.
  • Libraries supporting archive formats: TAR, CPIO, and AR.
  • The remaining libraries were about Deflate compression, the ELF file format, elliptic curve encryption, and QR code generation.

This analysis reflects my codebase. Other codebases may yield different results.

Does the ceilDiv operator improve readability?

Following these findings, ceilDiv has been introduced into the libraries. Code like: 

header.blockLines := succ(pred(header.height) mdiv 8);
header.blockColumns := succ(pred(header.width) mdiv 8);
turned into: 
header.blockLines := header.height ceilDiv 8;
header.blockColumns := header.width ceilDiv 8;
This change, IMHO, improves readability. In other instances, the integer ceil division was located in the middle of an expression. For example: 
headPos := tell(tarFile) +
    succ(pred(header.fileSize) mdiv TAR_BLOCK_SIZE) *
    TAR_BLOCK_SIZE;
which turned into: 
headPos := tell(tarFile) +
    header.fileSize ceilDiv TAR_BLOCK_SIZE * TAR_BLOCK_SIZE;
At some places, the integer ceil division computes an index. Code like: 
readDcValue(mcuImg[succ(pred(line) mdiv hdr.vertical)]
                  [succ(pred(col) mdiv
                        hdr.horizontal)].luma[idx][1],
            entropyCodedStream, dcDecoder, diffLuminance,

turned into: 
readDcValue(mcuImg[line ceilDiv hdr.vertical]

            hdr.approximationLow);

Relationship between ceilDiv and floorDiv

The ceilDiv operation is closely related to the floorDiv operation. As the name suggests, floorDiv corresponds to (int) floor((double) a / (double) b). This is usually different from what standard integer / division provides. While integer / and floorDiv yield the same result for positive a and b, the behavior diverges if either a or b is negative. The Python // operator and the Seed7 mdiv operator both function exactly like floorDiv.

When floorDiv is available, a ceilDiv b can be expressed as: 

-(-a floorDiv b)
or as: 
    
-(a floorDiv -b)
Therefore, floorDiv can be used to implement ceilDiv.

Implementing ceilDiv in an interpreter

An implementation of ceilDiv in C, must handle several edge cases.

If b is zero, ceilDiv will trigger a division by zero. In this case, a NUMERIC_ERROR exception is raised.

Another edge case occurs when the most negative integer is divided by -1. Dividing a by -1 is equivalent to negating a. In a two's complement representation, negating the most negative integer causes an overflow. In this case, an OVERFLOW_ERROR exception is raised.

If dividend and divisor are both greater than 0, the formula: 

(a - 1) / b + 1
can be used. If dividend and divisor are both less than 0, the formula: 
(a + 1) / b + 1
can be used. In all other cases, the standard integer division: 
a / b
suffices. The actual C implementation of ceilDiv in the interpreter uses 38 lines of code.

Implementing ceilDiv in a compiler

Basically a compiler could use the same approach as the interpreter. But a compiler can do much more than that. If a and b are known at compile-time the result can be computed at compile-time. If the compiler knows that ceilDiv will fail it can generate code to raise an exception.

Some historic C compilers triggered the signal SIGFPE, if a division by zero occurred. This allowed for omitting explicit division by zero checks. But division by zero is undefined behavior and modern C compilers assume that undefined behavior never happens. Since C compilers cannot be trusted to check for division by zero the checks need to be inserted explicitly.

If one of a or b is known at compile-time formulas can be simplified. If b is known the formula 

(a - 1) / b + 1
which uses uses 3 instructions (-, / and +) could possibly be replaced with 
(a + b - 1) / b
which uses just 2 instructions (since b - 1 can be computed at compile-time). But with this formula an integer overflow could happen. So the compiler needs to assure that this integer overflow does not happen.

If b is known to be a power of two (b = 1 << n) the division could be replaced by a right shift. Shifts are much less costly than divisions. So this brings a performance boost. In modern C right shifts are arithmetic. This creates the additional advantage that no check a > 0 or a < 0 is necessary. This allows the formula 

((a - 1) >> n) + 1
which uses 3 instructions (-, >> and +). This could overflow if a is the most negative integer. The compiler must take care that this does not happen. There is another formula for this case 
(a + b - 1) >> n
which uses 2 instructions (since b - 1 can be computed at compile-time). This could overflow as well and the compiler needs to take care of it.

Even if exact values of a and b are not known at compile-time there might be hints which range of values are possible for a or b. It could be known at compile time that b is in the range l .. u. If this range does not contain zero it is not necessary to check for a divide by zero. If this range does not contain -1 the check for a / -1 is not necessary.

All these combinations lead to 33 cases and all of them need to be considered. The actual implementation of ceilDiv in the compiler uses 596 lines.

Testing the ceilDiv implementation

Interpreters and compilers need to assure that their functionality is trustworthy in all situations. This is done with a test suite. New tests needed to be added to cover the ceilDiv operation. The tests cover basic ceilDiv functionality, corner cases and the different optimization aproaches used by the compiler. The ceilDiv tests where carefully crafted to reach 100% code coverage of the corresponding compiler code.

The tests need to distinguish between things known at compile-time and things that are not known at compile time. Tests use the function intExpr(number) which returns its argument. This function is constructed in a way that makes it impossible for the compiler to discover that the argument is returned. This way the compiler views e.g. intExpr(2) as an integer unknown at compile time.

The tests check the expression 2 ceilDiv 5 four times: 

        2  ceilDiv         5
intExpr(2) ceilDiv         5
        2  ceilDiv intExpr(5)
intExpr(2) ceilDiv intExpr(5)

This covers the combinations of what is known or unknown at compile-time.

The compiler also uses ranges of possible values for decisions. The expression 

abs(intExpr(5))

tells the compiler that number >= 0 holds. Similar tricks can be useed to encode that number > 0, number < 0, number <= 0 or number < -1 holds.

This allows tests like: 

if integer.first ceilDiv pred(-abs(intExpr(integer.last))) <> 1 then

The tests for ceilDiv in the test suite use 3239 lines in two test programs.
