Integer ceil division

An integer ceil division corresponds to (int) ceil((double) a / (double) b). This converts the values to double, divides them, and rounds the quotient up to the nearest integer. If you have a block size of 512 and want to calculate the number of blocks needed to store n bytes, then n ceilDiv 512 provides the answer.

Since floating-point operations are costly, the alternative for computing an integer ceil division is (a + b - 1) / b, which just uses integer computations. Another method is (a - 1) / b + 1. Both formulas assume that a and b are positive integers. For negative numbers, the computation becomes more sophisticated.

How often are integer ceil divisions used?

I searched my source code and found integer ceil divisions in 14 different libraries. In total, 45 integer ceil divisions were found. I did not expect to find so many. In all of these cases, one of the integer formulas mentioned above was used. While the code was correct and readable, a closer look was required to realize that an integer ceil division was actually being performed.

The libraries utilizing ceil division fell into three categories:

  • Libraries supporting graphics formats: JPEG, BMP, TIFF, ICO, TGA, and PBM.
  • Libraries supporting archive formats: TAR, CPIO, and AR.
  • The remaining libraries were about Deflate compression, the ELF file format, elliptic curve encryption, and QR code generation.

This analysis reflects my codebase. Other codebases may yield different results.

Does the ceilDiv operator improve readability?

Following these findings, ceilDiv has been introduced into the libraries. Code like: 

header.blockLines := succ(pred(header.height) mdiv 8);
header.blockColumns := succ(pred(header.width) mdiv 8);

turned into: 

header.blockLines := header.height ceilDiv 8;
header.blockColumns := header.width ceilDiv 8;

This change, IMHO, improves readability. In other instances, the integer ceil division was located in the middle of an expression. For example:

Relationship between ceilDiv and floorDiv

The ceilDiv operation is closely related to the floorDiv operation. As the name suggests, floorDiv corresponds to (int) floor((double) a / (double) b). This is usually different from what standard integer / division provides. While integer / and floorDiv yield the same result for positive a and b, the behavior diverges if either a or b is negative. The Python // operator and the Seed7 mdiv operator both function exactly like floorDiv.

When floorDiv is available, a ceilDiv b can be expressed as: 

-(-a floorDiv b)

or as: 

-(a floorDiv -b)

Therefore, floorDiv can be used to implement ceilDiv.

Implementing ceilDiv in an interpreter

An implementation of ceilDiv in C, must handle several edge cases.

If b is zero, ceilDiv will trigger a division by zero. In this case, a NUMERIC_ERROR exception is raised.

Another edge case occurs when the most negative integer is divided by -1. Dividing a by -1 is equivalent to negating a. In a two's complement representation, negating the most negative integer causes an overflow. In this case, an OVERFLOW_ERROR exception is raised.

If dividend and divisor are both greater than 0, the formula: 

(a - 1) / b + 1

can be used. If dividend and divisor are both less than 0, the formula: 

(a + 1) / b + 1

can be used. In all other cases, the standard integer division: 

a / b

suffices. The actual C implementation of ceilDiv in the interpreter uses 38 lines of code.

Implementing ceilDiv in a compiler

Basically, a compiler could use the same approach as the interpreter. However, a compiler can do much more than that. If a and b are known at compile-time, the result can be computed at compile-time. If the compiler detects that ceilDiv will fail, it can generate code to raise an exception.

Some historic C compilers triggered the signal SIGFPE if a division by zero occurred, which allowed for omitting explicit division by zero checks. But division by zero is undefined behavior, and modern C compilers assume that undefined behavior never happens. Since C compilers cannot be trusted to check for division by zero implicitly, these checks must be inserted explicitly.

If either a or b is known at compile-time, the formulas can be simplified. If b is known, the formula: 

(a - 1) / b + 1

which uses 3 instructions (-, /, and +) could possibly be replaced with: 

(a + b - 1) / b

which uses just 2 instructions (since b - 1 can be computed at compile-time). However, an integer overflow could happen with this second formula. The compiler must therefore ensure that this integer overflow cannot occur.

If b is known to be a power of two (b = 1 << n), the division can be replaced by a right shift. Shifts are much less costly than divisions, bringing a substantial performance boost. In modern C, right shifts on signed integers are arithmetic. This creates the additional advantage that no check for a > 0 or a < 0 is necessary, allowing the formula: 

((a - 1) >> n) + 1

which uses 3 instructions (-, >>, and +). This could overflow if a is the most negative integer, so the compiler must take care that this does not happen. Another formula for this case is: 

(a + b - 1) >> n

which uses 2 instructions (since b - 1 can be computed at compile-time). This could overflow as well, and the compiler needs to account for it.

Even if the exact values of a and b are not known at compile-time, there might be hints about what range of values are possible for them. If it is known at compile-time that b is in the range l .. u, and this range does not contain zero, it is not necessary to check for a division by zero. Similarly, if this range does not contain -1 the check for a / -1 is not necessary.

All these combinations lead to 33 cases, and all of them need to be considered. The actual implementation of ceilDiv in the compiler uses 596 lines of code.

Testing the ceilDiv implementation

Interpreters and compilers must guarantee that their functionality is trustworthy in all situations. This reliability is ensured with a test suite. New tests were added to cover the ceilDiv operation. These tests cover basic ceilDiv functionality, edge cases and the various optimization approaches used by the compiler. The ceilDiv tests were carefully crafted to achieve 100% code coverage of the corresponding compiler code.

The test suite must distinguish between values known at compile-time and values unknown at compile time. To achieve this, the tests utilize an identity function, intExpr(number), which simply returns its argument. This function is constructed in a way that prevents the compiler from discovering that the argument is returned unchanged. This way the compiler views e.g. intExpr(2) as an integer value unknown at compile-time.

Using this mechanism, the tests check an expression, such as 2 ceilDiv 5, four times: 

if          2  ceilDiv         5  <> 1 or
    intExpr(2) ceilDiv         5  <> 1 or
            2  ceilDiv intExpr(5) <> 1 or
    intExpr(2) ceilDiv intExpr(5) <> 1 then ...

This covers the combinations of parameters being either known or unknown at compile-time.

Because the compiler also uses known ranges of possible values to make optimization decisions, the test suite explicitly triggers these optimization paths. For instance, the expression: 

abs(intExpr(5))

informs the compiler's range analysis that number >= 0 holds. Variations of this expression are used to encode constraints such as number > 0, number < 0, number <= 0, or number < -1.

This allows tests like: 

integer.first ceilDiv pred(-abs(intExpr(integer.last))) <> 1

In this case, the compiler knows that the dividend is integer.first and that divisor < 0 holds. At run-time the test just checks: 

integer.first ceilDiv integer.first <> 1
